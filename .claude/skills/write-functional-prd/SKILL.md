# 功能 PRD 撰写

## 目标

生成与原型配套、供产品评审和研发实现使用的最小充分 PRD。让研发能够明确谁可以操作、何时可以操作、系统如何处理、数据或状态如何变化、失败时如何处理。

## 使用参考文件

- 新建 PRD 或调整整体结构前，读取 [prd-structure.md](references/prd-structure.md)。
- 编写页面、流程、状态、校验、列表或表单需求时，读取 [writing-patterns.md](references/writing-patterns.md)。
- 交付前，读取并执行 [quality-checklist.md](references/quality-checklist.md)。

## 处理输入

1. 读取用户提供的需求、业务材料、现有 PRD、原型和关联文档。
2. 按以下顺序判断事实优先级：用户当前明确要求 > 已确认的正式需求或 PRD > 业务规则和系统资料 > 原型或现有系统表现。
3. 从原型提取功能入口、用户操作、页面状态和数据内容；不要将视觉参数、演示数据或临时交互提升为产品需求。
4. 区分已知事实、可选设计建议、缺失信息和相互冲突的信息。
5. 仅在缺失信息会显著改变核心流程、权限、数据或本期范围时提问。其余未决事项集中写入“待确认问题”，不要自行编造结论。

## 撰写流程

1. 明确业务背景、本期目标和不在范围内的事项。
2. 建立角色、功能权限、数据范围、关联系统和核心业务对象。
3. 梳理主流程及必要的失败、中断和恢复分支。
4. 定义影响操作的状态、状态变化和关键校验。
5. 形成带优先级和本期标识的功能清单。
6. 按客户端、模块和页面编写功能需求。
7. 检查功能清单、权限、状态、规则和页面需求是否一致。
8. 删除不影响功能实现的文字后再交付。

## 内容边界

### 必须描述

- 角色职责、功能权限和数据范围。
- 功能入口、前置条件和适用状态。
- 数据来源、展示范围、筛选、排序、分组和计算口径。
- 用户操作、业务校验、系统处理、数据或状态变化。
- 非显而易见的空状态、失败、重复操作、中断和恢复处理。
- 页面之间的业务跳转和必要的数据传递。
- 与其他模块或系统的业务依赖。
- 本期范围、非本期范围和确有必要的待确认问题。

### 默认省略

- 字体、颜色、尺寸、间距、圆角、阴影、坐标和其他视觉规格。
- 原型已经清楚表达且不影响逻辑的布局、静态文案和控件位置。
- 返回上一页、关闭普通弹窗、常规展开收起等无特殊结果的通用交互。
- “页面简洁美观”“提升用户体验”等无法指导实现的表述。
- HTML、CSS、组件、函数、数据库表和具体接口实现方案。
- 与当前功能无关的远期设想。

仅当界面行为直接影响业务、安全、权限或操作结果时描述该约束，并使用结果导向的语言。例如写“告警在风险解除前持续显示”，不要写具体颜色和高度。

## 写作规则

1. 先写业务结论，再写必要的条件和分支。
2. 使用短句、编号列表和必要的表格，避免长篇解释。
3. 关键功能按照“用户操作 -> 前置条件或校验 -> 系统处理 -> 数据或状态变化 -> 失败处理”描述。
4. 页面需求默认使用“一个页面标题 + 连续编号描述 + 必要表格”。将默认状态、数据展示、操作、校验、结果和跳转融合在实际操作顺序中，不机械拆分小节。
5. 仅当不同角色、客户端或状态产生明显功能差异，或者字段、状态、校验较复杂时再增加小标题或表格。
6. 同一规则只完整定义一次；其他位置简短引用对应章节，不重复改写。
7. 同一概念全篇使用同一名称。沿用用户或现有正式文档中的术语，不擅自创造近义词。
8. 对字段、权限、状态、校验、功能清单等重复结构使用表格；对连续业务流程使用编号列表。
9. 仅在提示内容承载阻断原因、业务后果或合规要求时给出精确文案，否则只说明需要反馈的结果。
10. 没有实际内容的章节、表格和列表直接删除，不为保持模板完整而填充文字。

## 输出与修改

- 使用 Markdown 输出；用户指定文件时写入指定文件，否则使用 `{模块名称}PRD.md`。
- 修改现有 PRD 时保留已确认内容，只修改受影响部分，并更新版本记录。
- 版本记录只记录功能范围、业务规则、数据或权限变化，不记录视觉调整和代码修复过程。
- 交付回复只说明文件位置、核心范围和仍需确认的关键问题，不重复粘贴全文。
